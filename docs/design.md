# 设计

Loadlet 将“如何得到结果”和“何时重新求值”分别建模。前者通过加载器与处理函数表达，后者由会话和监听适配器负责。调用方使用同一份加载请求，既可以执行一次，也可以持续维护结果。

## 一次加载

每轮按固定顺序执行：加载来源，完成可选处理，再发布成功快照。

```text
source → loader.load → 初始值 → process（可选）→ 成功快照
             │                      │
             └──── 登记输入依赖 ────┘
```

| 组成                | 作用                                             |
| ------------------- | ------------------------------------------------ |
| `source`            | 加载器接受的来源描述，如文件 URL 或用户对象      |
| `Loader<S, I>`      | 从来源取得初始值，并登记读取涉及的文件           |
| `Processor<I, O>`   | 将初始值处理成发布值，可组合解析、合并和校验函数 |
| `EvaluationContext` | 提供本轮编号、取消信号与依赖登记能力             |
| `Snapshot<T>`       | 保存成功值、版本和本轮依赖，供消费者使用         |

`LoadRequest<S, I>` 表达直接采用加载值的请求；`ProcessedLoadRequest<S, I, O>` 增加处理函数。名称描述传给 `load` 或 `open` 的数据，结果类型从加载器和处理函数推导。泛型保留输入与输出的关系，符合 [TypeScript 泛型接口](https://www.typescriptlang.org/docs/handbook/2/generics.html)的常规用法。

## 扩展方式的选择

Loadlet 采用可替换策略与函数组合：`Loader`、`Watcher` 承载可复用适配能力，`process` 承载每个使用场景的转换规则。固定执行顺序让核心能够统一决定成功提交、失败保留和资源释放。

| 实践         | 适用能力                                 | Loadlet 的选择                                                       |
| ------------ | ---------------------------------------- | -------------------------------------------------------------------- |
| 函数组合     | 按数据类型连接多个处理步骤               | 用户在 `process` 内组合函数，同步返回值和 Promise 使用统一调用方式   |
| 策略与回调   | 替换某项能力，同时保留外层流程           | 加载与监听使用结构化接口，结果处理使用单个函数                       |
| 管道与过滤器 | 组合可复用步骤，按输入输出连接并调整顺序 | 数据转换由用户函数表达；可复用步骤已有具体需求时，再评估独立编排能力 |
| Hook         | 多个插件在约定阶段参与执行               | 当前扩展点直接作为请求与会话参数传入；新增阶段需有独立的输入输出契约 |
| 中间件       | 将继续执行或提前结束的控制权交给扩展     | 当前由核心掌握每轮执行和提交，扩展通过返回值或抛错完成工作           |

管道与过滤器强调独立步骤之间的组合关系，可参见 [Microsoft 架构模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/pipes-and-filters)。Hook 系统还需要定义多参与者的顺序与结果合并，例如 [Rollup 的 Hook 分类](https://rollupjs.org/plugin-development/#build-hooks)；中间件则包含控制权传递，例如 [Express 的 `next()`](https://expressjs.com/en/guide/using-middleware/)。这些实践提供设计参照，当前需求采用表中的组合方式。

因此，公开接口由加载请求和会话组成。步骤的动态注册、排序与 `next` 调度暂不进入接口；用户仍可通过普通函数组织复杂处理。

## 会话与结果发布

`load()` 完成一轮求值并返回快照。`open()` 建立监听并取得首个成功快照，之后以同一请求持续求值。

会话串行运行加载与处理，合并连续失效请求。已过期轮次不会发布；有效轮次全部成功后才更新 `current` 和成功版本。更新失败时保留旧快照及恢复依据，相关文件变化后重试。关闭会阻止新更新，并等待在途求值和资源清理。

这一生命周期集中在核心，加载器和使用者都可以围绕稳定的结果接口工作。事件顺序、取消与清理失败的细节见 [行为契约](contracts.md)。

## 依赖与适配器

依赖由读取行为决定。文本处理可能包含其他文件，模块执行可能涉及传递导入；加载和处理阶段共享 `track(file)`，登记影响结果的本地文件。`readText` 在读取前完成登记，自定义读取也应遵守这一顺序。

每次变化重新执行整轮，因此核心保存足以触发失效的文件集合。模块图、解析规则和模块缓存由执行适配器管理。成功轮替换有效集合，失败轮留下恢复依据，以支持缺失文件的后续创建。

| 包                | 所有的能力                     | 接入核心的接口                           |
| ----------------- | ------------------------------ | ---------------------------------------- |
| `loadlet`         | 调度、快照、诊断、恢复、终止   | `load`、`open`、`Session`                |
| `@loadlet/node`   | 文本读取、本地文件变化通知     | `Loader`、`EvaluationContext`、`Watcher` |
| `@loadlet/module` | JS/TS 执行、依赖发现与重新求值 | `Loader`、`EvaluationContext`            |

独立文件监听和宿主 watcher 都通过 `Watcher` 接入。每个会话持有自己的监听连接，释放时只影响自身登记。各适配器的能力范围和资源责任见 [适配器契约](adapters.md)。

## 消费者的职责

消费者定义结果的业务含义：选择来源、解析格式、合并层级、校验结构。会话内的请求与环境参数保持稳定，需要切换环境时建立新会话。

成功快照表示加载与处理已完成。数据库重连、文件生成等采用结果的操作由消费者调度，并通过快照的 `id` 与 `version` 关联；其错误由业务逻辑处理。已发布值由使用者遵守稳定性约定，具体所有权规则见 [行为契约](contracts.md)。
