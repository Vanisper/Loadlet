## 求值与结果

一次求值依次执行 `loader.load` 和可选的 `process`，等待各阶段返回的 Promise。加载失败时停止后续处理；全部成功后发布一个完整结果。省略 `process` 时采用加载值，`undefined`、`null` 和空文本都是合法结果。

| 入口   | 完成条件                           | 失败行为                                         |
| ------ | ---------------------------------- | ------------------------------------------------ |
| `load` | 执行一轮，返回成功快照             | 释放本轮资源后拒绝；不建立持续监听               |
| `open` | 先连接 watcher，再取得首个有效快照 | 被变化取代时等待补跑；有效轮失败时释放资源并拒绝 |

### 输入与值的所有权

会话期间，来源、加载器、处理函数及其依赖的环境参数固定，由调用方保持稳定。核心保留这些对象的引用；环境或来源语义变化时，关闭旧会话并重新打开。

结果可以是函数、Map、类实例等任意值。核心冻结快照外壳和依赖数组，`value` 保留原值。生产者和消费者负责保持已发布对象及其可达状态稳定；引用可变单例时，应在发布前复制或转换。核心不会深度克隆、冻结或就地修改用户值。

| 快照字段       | 含义                                             |
| -------------- | ------------------------------------------------ |
| `id`           | 一次加载或会话的独立标识，版本只在相同 id 内比较 |
| `version`      | 从 1 开始，每次成功发布递增；值相等也发布新版本  |
| `attempt`      | 求值尝试编号，失败与被取代的轮次同样占用编号     |
| `dependencies` | 本次成功求值的依赖集合，不含其他轮次的恢复目标   |

关闭后，最后成功快照仍可读取。加载与处理的成功表示结果可供消费；数据库连接、文件生成等采用结果的业务操作由消费者管理。

## 依赖与恢复

### 登记输入

加载和处理通过同一个 `EvaluationContext` 登记依赖。每次读取前须 `await context.track(file)`；文本加载器登记入口，`readText` 登记附加文件，自定义加载器登记自己的全部输入。

| 项目     | 规则                                                                          |
| -------- | ----------------------------------------------------------------------------- |
| 目标     | 无查询参数和片段的绝对 `file:` URL，指向精确文件                              |
| 缺失目标 | 文件及其父目录均可尚不存在，登记用于捕获后续创建                              |
| 身份     | 保存登记时规范化的 `href` 副本，按字符串去重、排序；原 URL 后续变化不影响记录 |
| 就绪     | 持续会话中等待监听就绪；一次加载中仅记录依赖                                  |
| 生命周期 | 本轮结束、被取代或关闭后，旧 context 的新登记拒绝                             |
| 无效输入 | 类型或 URL 无效时，以 `INVALID_DEPENDENCY` 使本轮失败                         |

依赖集合描述会影响结果的输入。符号链接的访问路径与真实读取目标、平台大小写和事件映射由适配器处理，规范化不依赖当前 cwd。目录、glob 和网络目标的自动监听不在首版范围内。

### 成功集合与恢复集合

设 `S` 为最后成功依赖，`F` 为上次成功以来未提交轮次的依赖并集，`A` 为本轮已登记依赖。

| 时点         | 监听集合    | 快照与集合变化                       |
| ------------ | ----------- | ------------------------------------ |
| 初始化       | `A`         | 等待首个成功结果                     |
| 更新中       | `S ∪ F ∪ A` | 保留 current                         |
| 失败或被取代 | `S ∪ F ∪ A` | `F = F ∪ A`，保留 current 和成功版本 |
| 有效轮成功   | 新的 `A`    | 发布结果，`S = A`，`F = ∅`           |

成功提交按“确认新监听就绪 → 移除多余监听 → 发布快照”执行。移除期间发生相关变化时，本轮过期，恢复所需监听并补跑。已退役目标的迟到事件会被过滤；当前轮和恢复集合中的事件仍然有效。

恢复集合保留到下一次成功或关闭，连续失败时可累计增长。这样，即使后续失败发生得更早，之前发现的缺失文件仍可触发恢复。首版不使用 TTL 静默淘汰恢复目标。

### 变化与恢复

已有会话加载或处理失败时报告诊断，保留成功快照；相关输入变化或手动 `reload()` 触发完整求值。等待期间不进行无限定时重试。

入口缺失默认是加载错误。需要默认值的加载器可先登记入口，再明确处理缺失情况并返回默认值；后续创建入口仍应触发重载。

每个目标的读取窗口都必须受到监听保护。适配器须在读取前完成登记，或提供经验证的等价机制，在安装期间缓冲事件或校验补发；仅在执行成功后返回依赖列表不足以满足此要求。具体规则见[监听协议](adapters.md#监听协议)。

## 调度

同一会话严格串行执行加载和处理。文件事件与 `reload()` 推进失效代次；在途轮次之后最多保留一个待执行位置，连续请求可合并。

新失效会标记在途轮次过期并发出 AbortSignal。等待该轮退出和清理后开始下一轮，过期结果不发布。不响应取消的用户函数会延迟补跑与关闭，核心不会启动并行轮次绕过它。

### reload 的完成语义

`reload()` 等待覆盖本次请求、且未被取代的有效轮次。

| 后续情况         | 等待者结果                           |
| ---------------- | ------------------------------------ |
| 有效轮成功       | 返回成功快照；多个请求可共享同一快照 |
| 轮次被取代       | 继续等待，过期轮的成功或失败均不结算 |
| 有效轮失败       | 以相同主要诊断拒绝，保留 current     |
| 显式关闭         | 以 `SESSION_CLOSED` 拒绝未结算请求   |
| 外部 signal 中止 | 以 `ABORTED` 拒绝未结算请求          |

持续变化可能延迟结算。加载器和处理函数不能等待同一会话的 `reload()` 或 `close()`，否则当前求值会等待自身结束；生命周期由外层宿主控制。

## 订阅

会话推送 `snapshot` 与 `diagnostic` 两类事件。普通通知按提交顺序同步投递，监听者按注册顺序调用。

| 操作或情况               | 行为                                                                 |
| ------------------------ | -------------------------------------------------------------------- |
| `subscribe`              | 同步登记并立即交付 current，历史诊断不回放                           |
| 回调内新增订阅           | 立即回放 current；新订阅不再参与当前广播，避免重复交付               |
| 其他重入通知             | 排队投递，保持顺序                                                   |
| 取消订阅                 | 幂等；停止尚未开始的投递，已执行回调无法撤销                         |
| 回调抛错                 | 取消该订阅，向其余订阅者排队报告 `SUBSCRIBER_FAILED`，继续原事件投递 |
| 诊断回调再次抛错         | 同样取消该订阅，避免向失败监听者递归通知                             |
| 回调内调用 `close()`     | 立即阻止后续尚未开始的通知，包括当前广播                             |
| closing 或 closed 时订阅 | 同步抛出 `SESSION_CLOSED`                                            |

同步回放消除了读取 current 与注册监听之间的遗漏窗口；订阅失败不会回滚成功快照。

监听函数的类型要求同步返回 `undefined`。业务异步任务由消费者调度并处理错误，`reload()`、`close()` 的 Promise 也不返回给通知系统。JavaScript 调用者误传 async 回调时，核心不等待 thenable，但必须消费其拒绝：会话开放时按订阅失败处理，关闭开始后仅消费拒绝，不再通知。

## 终止与诊断

### 错误信息

`load`、`open`、`reload` 通过 `LoadletError` 报告失败。`diagnostics[0]` 为主要原因，清理失败追加其后；原始原因保留在 `cause`。一般加载和处理异常分别使用 `LOAD_FAILED`、`PROCESS_FAILED`；适配器或 `track` 抛出的合规 `LoadletError` 保留原诊断顺序与具体代码。

诊断使用 `code` 供程序判断，`message` 供人阅读。有可靠归属时提供文件与 attempt。被取代轮次的求值错误不作为当前失败通知，其依赖仍用于恢复；清理错误仍须单独报告，关闭期间则进入清理结果。

### 监听故障

`connect`、`add`、`remove` 失败，或 watcher 报告监听完整性丢失时，以 `WATCH_FAILED` 终止会话：

1. 保留 current，立即拒绝新请求并禁止发布
2. 向现有订阅者交付最后一条故障诊断
3. 释放资源并进入 closed

第二步是终止后唯一允许的通知。故障回调若显式调用 `close()`，仍会截断尚未开始的广播。恢复使用需要重新打开会话。

### 取消与关闭

`options.signal` 对 `load` 控制单轮求值，对 `open` 覆盖整个会话。调用前或初始化期间中止，以 `ABORTED` 拒绝并清理；打开后中止则自动开始关闭。

关闭按以下顺序执行：

1. 同步进入 closing，停止新请求和通知；监听故障的终止通知遵循上一节
2. 取消排队轮次，拒绝等待者，中止在途轮次
3. 等待在途加载、处理及其清理结束
4. 释放本会话的 watcher 连接与核心资源
5. 进入 closed，完成全部关闭等待者

`close()` 幂等，共享同一清理结果。释放失败通过 `CloseResult.diagnostics` 返回，会话仍保持 closed；初始化失败则将清理诊断附加到拒绝错误。释放失败的适配器也必须停止本连接的通知入口。关闭完成后不再通知或发布，已知释放失败不能作为资源释放成功报告。

关闭等待范围是核心拥有的工作与资源。消费者负责停止接收、等待自己启动的业务任务，并释放结果中包含的资源；核心不隐式调用用户值的 dispose。不响应取消的用户函数可能使关闭持续等待。

## 保证范围

自动更新覆盖已登记文件及适配器声明支持的文件系统，以有效事件交付为前提。事件用于触发重算，不要求逐一复现瞬时中间态。隐式 I/O、环境变量、时间和网络变化需要调用方显式建模；特殊文件系统、网络挂载和容器映射需分别验证。

一次求值可能读到不同时间点的多个文件。需要跨文件一致性时，加载器或处理函数应检查自己的版本标记。模块与用户函数在宿主进程中执行，隔离沙箱、副作用回滚和强制内存回收不属于首版保证。
